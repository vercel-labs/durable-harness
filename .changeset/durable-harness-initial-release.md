First release: durable coding-agent harnesses on a Workflow SDK World. Claude Code (`durable-harness/claude-code`), Codex (`/codex`), OpenCode (`/opencode`) and Pi (`/pi`) each run as an agent whose session is a workflow run, its event log the source of truth: every model and tool call is a step in the log, so a crash anywhere resumes the turn from the log on another machine, and a tool that is not safe to rerun comes back to the model as interrupted instead of running twice. Claude Code and Codex run only in the session's own Vercel Sandbox (`workspace: sandbox()`, the default): the CLI runs in a VM per session with the session's Drive at `/workspace`, holds no credential (the Function makes its model calls, within the session's `sandbox({ budget })`), and a session restarted on a new VM keeps its files and resumes from the log. Both are tool-less by default: the app's tools are the only ones the CLI is offered; `builtins: true` turns its own tools on in the VM, each call in the log before it runs. `durable-harness/sandbox` deletes a session's VM and Drive (`deleteSessionSandbox`), cleans up idle ones (`sandboxCleanup`, opt-in), and prepares the base snapshot ahead of time (`npx durable-harness sandbox prepare`); a public chat route for such an agent needs `allowPublicSandbox: true`. OpenCode is tool-less too, starts no process and reads no file of the machine that drives the session for the model, and never changes the process's environment (so it runs beside libfx's agents in one process); `workspace: virtual()` on `opencode()` gives it its own shell, read, write, edit, patch, glob and grep (OpenCode's own tool code, names and schemas) on a virtual workspace, each call's file changes committed with its result, never on the Function's disk (`builtins` narrows them); `workspace: sandbox()` runs the same tools in the session's own Vercel Sandbox, its files on the session's Drive, the VM booted at the first call that needs it. A turn whose installed OpenCode or `effect` isn't the pinned version fails with both versions and the install line. Each agent has a streaming chat route (`agent.chatRoute()`, with an `authorize` check required in production). For apps already built on Pi 1.0's own durable `Harness` (pi-durable), `durable-harness/pi-durable` adds to your code instead of replacing it: open the storage with `openWorldStorage()` where you opened SQLite, JSONL or memory storage, register how a session is reopened with `resumeWith(open)`, and if the process dies mid-turn a wake reopens the session and Pi finishes the turn; `CodingTools` and `env: virtualEnv()` from the same module run Pi 1.0's own coding tools on a virtual workspace, each call's file changes committed with its result, never on the Function's disk, and `env: sandboxEnv()` runs them in the session's own Vercel Sandbox, its files on the session's Drive, armed with the session's own fencing token; a chat route, a shared Harness per session and a read-only follower are optional helpers. `withDurableHarness` (`/next`) sets up the queue's route for Next.js and also serves libfx's durable agents (several, each with its own `name`, with libfx 0.0.14 and later); `/vercel` does the same for Vercel Functions. Self-hosted on world-postgres or world-local, a process that starts the World without making agents (a worker of its own) forwards durable-harness's queue to the app's flow route with `forwardQueue(world)`. Sessions show up in Vercel Agent Runs with their model and tool calls (`agentRuns()` from `/instrumentation/otel`, with OpenTelemetry's SDK installed next to it: optional peers, which nothing else loads), pi-durable's included: a `traceAudience` on `openWorldStorage()` or `resumeWith()` says who sees their content. Pi is tool-less by default; `createCodingTools(virtual())` from `/pi` gives it Pi's own `read`, `bash`, `edit` and `write` (pi-coding-agent's names, schemas and descriptions) on a virtual workspace, or with `createCodingTools(sandbox())` in the session's own Vercel Sandbox (Pi stays in the Function, the VM is attached on the first call), and `pi()` refuses pi-coding-agent's own tools, which run on the host. Also included: documents (typed JSON state per session, `defineDoc`) and example workspace tools (`/tools`) on a virtual workspace (`virtual()`): not real Linux, and nothing of the machine that drives the session (its shell runs in a worker thread leased to that session alone, with an empty environment and a time limit per command), its files in the log, or with `virtual({ durable: false })` in memory for one turn. For libfx's own durable agent (`createFxAgent`), `durable-harness/fx` adds libfx's kernel tools on a virtual workspace (`tools: [...fxTools(virtual())]`): fx's names and schemas, each call's file changes kept with the session and never applied twice; `fxTools(sandbox())` runs them in the session's own Vercel Sandbox, armed with the libfx lease of the worker that runs the call, so a server that was taken over runs nothing more there. Experimental: patch releases only while on 0.0.x.
